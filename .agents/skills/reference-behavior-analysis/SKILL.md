# Reference Behavior Analysis

Start with `Docs/DEEP-UI-AUDIT.md`, `Docs/PARITY-STATUS.md`, `Docs/SOUND-FORMATS.md`, `Docs/CONVERSION-STATUS.md` and linked issue evidence. Existing records describe Sunday Keys 2.5.2 Mac in Demo Mode; re-check version/access scope before any new comparison. StageKeys is independent and need not copy every reference feature.

Label each finding VERIFIED (direct reproducible observation/test with artifacts), DOCUMENTED (source/manual/repository statement not independently reproduced here), INFERRED (hypothesis explaining evidence) or UNKNOWN (unobserved/blocked). A document saying a test once passed is DOCUMENTED until its relevant conditions/artifacts are checked. Give every compatibility claim its narrow tested domain and counterexamples.

For UI/workflows capture app/build, OS, entitlement state, starting state, exact actions, values, result and screenshots without private material. For audio/MIDI capture instrument identity, route, sample rate/block size, gain staging, parameter values, MIDI sequence, render/capture method and fixture authorization. Unmatched instruments/routing are not a null test. Similar spectra, UI ranges or an MIT upstream comparison do not establish proprietary sonic equivalence.

Map observations to issue acceptance and distinguish intentional StageKeys design from missing support. Record blocked Prime/Ultimate/cloud behavior rather than probing access controls. Use [REA](../rea-reference-investigation/SKILL.md) only for authorized artifact/runtime investigation that ordinary source reading cannot answer. No proprietary code/art/sample redistribution. Keep one versioned evidence record with source links, hashes where appropriate, uncertainty and next discriminating experiment; do not promote an inference because multiple agents agree.
